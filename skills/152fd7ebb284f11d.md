# Evidence Video

Turn material into a reviewable Chinese knowledge video and an explicit publication package. The host agent supplies research, multimodal reading and editorial judgment; the bundled Node tools handle reproducible files, timing and rendering.

## Start

Locate this skill directory from the skill path. Use its absolute `scripts/video.mjs` path in commands. Project files belong in a user-owned output directory, never inside the installed skill or its plugin cache.

```text
node <skill>/scripts/video.mjs doctor
node <skill>/scripts/video.mjs init --project <absolute-project-directory>
node <skill>/scripts/video.mjs help
```

Node 24 is required. `init --example` creates a clearly labelled fictional demo. For real material, use normal `init`; an empty storyboard is intentionally not renderable. Follow the emitted next action. `setup` installs the pinned renderer dependencies into that project's renderer directory; respect the host's normal install permissions.

Use the user's material, platform, length, voice and style choices. When unspecified, use Chinese, 1080×1920/30fps, a concise explainer, and a calm natural voice. Do not import the author's historical topics, private paths, voice credentials, account identities or scheduled jobs.

A draft-only request uses `prepare --preview` and `publish-package --preview`; TTS and dependency installation are unnecessary for the HTML draft. If a multi-platform copy package is requested without named platforms, start with Bilibili and Douyin copy and state that choice. Actual publication always requires explicit destinations/accounts. Material `readingStatus` is the registration-time snapshot; it is not updated by the host's reading tools. Record reviewed claims and boundaries in the storyboard.

## Make or revise a video

1. Register provided files or URLs with `material`. Read the actual material using the host's file/vision/browser tools. For PDF, images or recordings, preserve page/frame/time references in notes. Registration only copies files or records URLs; it does not claim to have extracted or verified their contents.
2. Read [the storyboard contract](references/storyboard.md). Write `storyboard.json` in the project: source records, sourced claims, natural narration and original scene diagrams. Use primary evidence for changing claims. Distinguish reported facts, self-reports and editorial inference. A source link by itself is not proof of a claim. Mark fictional examples explicitly.
3. Run `validate` and `prepare`. Review the generated `output/review.html`, claim table and script. Resolve missing evidence and awkward language. If the user already authorized a complete video and there is no material ambiguity, continue without another routine confirmation; when they requested a draft, stop at that draft.
4. Run `render --mode stills` after renderer setup, inspect every materially different layout and the longest caption. Correct clipping, density and source/caption overlap. Do not claim visual review from successful compilation alone.
5. When the script is frozen and paid synthesis is within the user's authorization, follow [voice configuration and recovery](references/providers.md). Run `tts --dry-run` first, then `tts --allow-api`. Never put secrets in commands, model messages or output JSON. Use environment-variable references in config; keep actual secrets in the user's own environment or private env file.
6. Run `prepare` again. Exact segment durations determine captions and scenes. Timings are segment-level, not word-level forced alignment. Run final stills, then `render --mode video` when a completed video was requested. Use `qa` on the actual encoded file. Audio quality still requires listening; metadata/decoding checks are not a listening review.
7. Use `publish-package` to export each platform's copy, covers, provenance and media hash. Publication is a separate requested action; see below.

For changes, edit the editorial `storyboard.json`, then recompile. Existing voice receipts are reused only when the exact text and synthesis settings match. If a prior request has an uncertain outcome, inspect status before consenting to a targeted retry. Never re-run a whole paid batch because the host conversation resumed.

## Publish or prepare a release

Read [publication handoff](references/publishing.md) when preparing or publishing a video. A normal video request authorizes preparation, not public posting. Preserve explicit authorization already given in the session; a user may authorize an entire named batch once.

`publish-package` is a local export and does not contact social platforms. `publisher-plan` emits a reviewable adapter plan. A browser publisher's “dry-run” may upload real files: call it only when upload itself was authorized. Public posting must be scoped to the reviewed media, destination accounts, text, covers and schedule; changed content invalidates the approval. Keep credentials in the local publisher and expose only account labels and states to the model. Report confirmed platform receipts, not button clicks, as publishing evidence.

Do not auto-register accounts, schedule recurring posts, bypass platform authentication, or publish when the user only asked for installation or a preview.

## Deliver

Link the actual output, editable storyboard, review page and publication package. State whether audio was synthesized or attached, whether timing is estimated or audio-aligned, which checks ran, and whether anything was actually uploaded/published. If a dependency or provider is missing, return the working artifacts and exact next command; do not label a placeholder or silent demo as a finished voiced video.
